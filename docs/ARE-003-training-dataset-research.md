# ARE-003 — Training Dataset Research & ID Mapping

Дата проверки: 2026-11-10. Обучение не выполнялось. Результат исследования,
а не разрешение на автоматическое развёртывание ingestion или публикацию данных.

## Решение

Рекомендуется `mramazan/User-Animelist-Dataset` для следующего эксперимента ALS:
явная CC BY 4.0 в HF card, большой набор рейтингов, проверенное сопоставление MAL
и относительно современный каталог. Начать с Medium, а не со всех 148 млн строк.
Условие дальнейшей подготовки: согласовать политику конфликтующих рейтингов,
исключение нулей, происхождение объединённых источников и атрибуцию.
Не принимать заявление «freshly-created» за проверенную дату сбора.

Резерв: Hernan4444/2020 — предпочтительнее, если приоритетом станут статусы и
просмотры без оценок; его недостаток — старый каталог. CooperUnion/2016 удобен
для маленького технического baseline, но слишком стар для основного сервиса.

## Совместимость с YummyAnime

Ключ сопоставления:

`ratings.animeID -> animes.animeID -> MAL ID из mal_url -> YummyAnime.remote_ids.myanimelist_id`.

`animeID=1` в каталоге означает MAL 431; MAL 1 имеет другой внутренний ID.
Только у одной строки внутренний ID численно совпал с MAL ID. Прямое сравнение
`ratings.animeID == YummyAnime.myanimelist_id` недопустимо.
Парсер принимает только URL домена myanimelist.net с путём /anime/{positive ID};
неоднозначные mappings исключаются целиком, а не выбираются произвольно.

Проверены только два запроса собственного профиля: профиль и списки, HTTP 200/200,
только X-Application. Текущий снимок содержит 72 записи с 72 уникальными положительными
целочисленными MAL ID, без дубликатов. В каталоге найдены 66/72 (91,67%); 6/72
неизвестны этому каталогу. Среди items диагностической выборки найдены 51/72
(70,83%). Неизвестные IDs/названия не сохранялись в отчёте.

Это НЕ покрытие всего каталога YummyAnime и НЕ готовое покрытие ALS:
каталог присутствует целиком, но наличие положительных train-взаимодействий после
порогов ещё не проверено. Факторы шести отсутствующих items модель этого датасета
получить не сможет; число неизвестных после фильтрации может вырасти.
Проверять покрытие нужно заново на каждом зафиксированном train item vocabulary.

## Предлагаемая подготовка implicit feedback

Начальный, ещё не утверждённый эксперимент:

1. Проверить IDs, mapping и диапазон оценок. Нули/NaN исключать из positive
   feedback; не трактовать их как dislikes или доказанный просмотр.
2. Точные дубликаты удалить до split. Для пар с разными оценками без времени
   нет обоснования выбирать «последнюю»: исключить конфликтующие пары в baseline,
   измерить потери; медиану рассматривать только как отдельный эксперимент.
3. Positive: `rating >= 7`; проверить чувствительность к порогам 6 и 8 на validation.
   Оценки ниже порога не давать как положительные. В baseline оставить их вне
   sparse positive matrix, но сохранить в истории для исключения уже известных
   аниме из выдачи. Ненаблюдаемое не равно доказанному отрицательному отзыву.
4. Начать с одинаковой confidence наблюдаемых positives, например 10. Затем
   сравнить `c_ui = 1 + alpha * (1 + (rating-7)/3)` для rating>=7, alpha в {5,10,20}.
   В implicit передавать уже рассчитанную confidence и alpha=1, чтобы не умножать
   веса повторно. Эти значения — гипотезы, не выбранные по результатам обучения.
5. Низкие оценки 1–4 можно позднее проверить как explicit dislikes с отрицательной
   confidence по контракту implicit; не включать это в первый baseline.
6. Стартовые train-only пороги: >=5 positives на пользователя, >=5 пользователей
   на item; сравнить item threshold 10/20 по качеству и покрытию. Итеративную
   фильтрацию считать только на training partition. Для fold-in eval заранее
   выбирать пользователей с достаточным количеством positives для context+target,
   явно учитывать тех, кто потерял контекст после train-vocabulary filtering.

Online: тот же MAL mapping, item vocabulary и scaling. Высокие пользовательские
оценки совместимы с основной схемой; просмотрено без оценки и избранное — отдельные
сигналы, которых основной датасет явно не содержит. Их меньшие веса требуют отдельной
валидации; «в планах» не становится положительным просмотром автоматически.
Неизвестные items игнорируются для fold-in, но считаются в coverage; если контекст
пуст, нужен popularity fallback. Это предложение, реализация не входит в ARE-003.

## Протокол валидации без timestamps

Основной сценарий — новый пользователь, поэтому нужен user-disjoint split:

- Детерминированно по хешу userID+seed разделить пользователей на 80% train,
  10% validation, 10% test, не допуская одних users в разные части.
- Обучить item factors только на train-users; все статистики популярности,
  пороги, confidence и vocabulary строить на train. Split и policy версионировать.
- Для validation/test-users разделить дедуплицированные positives на context и
  targets, например контексты 3/5/10/20 с минимум одним target. Фиксировать seed.
  Неположительные известные items использовать только для фильтра seen, не targets.
- Получать пользовательский вектор через fold-in при замороженных item factors.
  Не дообучать item factors на context validation/test-пользователей.
- Recall@K, NDCG@K, HitRate@K считать на полном доступном train-каталоге, исключая
  context/известные неположительные items. Не ограничиваться случайными negatives.
  Coverage@K = уникальные рекомендованные items / размер train vocabulary.
- Отдельно сообщать долю mapped contexts, пользователей с пустым контекстом,
  OOV targets и conditional metrics по доступным targets. OOV targets учитывать
  как промахи в дополнительном end-to-end Recall/HitRate, а не молча удалять.
- Подбор параметров только на validation; test использовать после фиксации policy.
  Сравнивать ALS и popularity на одинаковых users, contexts, targets и candidates.

Без временных меток это восстановление скрытых предпочтений, НЕ прогноз будущего.
Случайный context может содержать более поздние просмотры, чем target; это ограничение
протокола, а не доказанная временная корректность. Дата релиза или порядок CSV
не заменяют timestamp взаимодействия. Объединение нескольких сайтов может содержать
одного человека под разными IDs: отсутствие такой утечки пока не доказано.

## Размер экспериментов и ресурсы

Выбирать полные истории пользователей по стабильному хешу, не первые N строк CSV.
Для построения такой выборки позже потребуется один потоковый проход исходного CSV;
диагностические byte windows непригодны как окончательная обучающая выборка.
Числа взаимодействий ниже — оценка по заявленному среднему 83,5, до фильтров.

| Вариант | Пользователи / строки | RAM машины | Свободный диск | CPU | Плановый бюджет времени |
|---|---|---|---|---|---|
| Small | 5 тыс. / ~0,42 млн | 4–8 GB | 3–5 GB, включая исходный CSV | 2–4 cores | минуты |
| Medium, рекомендуемый старт | 50 тыс. / ~4,2 млн | 8–16 GB | 5–8 GB | 4–8 cores | минуты–десятки минут |
| Full | 1,77 млн / 148 млн | 16–32 GB, предпочтительно 32 | 10–15 GB | 8–16 cores | десятки минут–часы |

Это инженерные бюджеты, НЕ измерения: модели не обучались. Предполагаются CPU ALS,
64 float32 factors, 15–20 iterations; точный срок зависит от solver, BLAS, CPU,
числа ненулевых элементов и oversubscription. Прежде чем Full, измерить один
Medium run и пиковую память. Не обещать линейный перенос времени.

Оценка памяти: CSR float32 data + int32 indices требует ~8*nnz+4*(U+1) байт.
Обе ориентации матрицы — около 16*nnz+4*(U+I+2): ~2,38 GB для 148 млн nnz.
Факторы float32 при 64 dimensions — ~0,46 GB для полного U+I.
Это нижняя оценка: COO staging, сортировки, pandas/Polars, дубликаты, рабочие буферы
и evaluation увеличивают пик. Dense U*I матрицу строить нельзя (~143,6 GB float32).

## Риски и границы результата

- Нули и дубликаты показывают, что card недостаточно для data contract.
- Полная нормализация оценок и дедупликация людей между MAL/AniList/Kitsu не проверены.
- Издательская лицензия не подтверждает права на любой исходный контент.
- Нет timestamps: невозможно честно воспроизвести временную оценку будущих просмотров.
- Полный каталог не равен активному train vocabulary; фильтрация снижает coverage.
- Один профиль не репрезентативен для аудитории YummyAnime.
- Статусы и favorites online отсутствуют в основной тренировочной схеме: domain gap.
- Возможны возрастные/региональные ограничения каталога; это отдельная будущая policy.
- Нет обучения, ingestion pipeline, базы данных, новых сервисов или публикации данных.
